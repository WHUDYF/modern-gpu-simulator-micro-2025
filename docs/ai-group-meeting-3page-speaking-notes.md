# AI GPU 研究方向组会 3 页口头汇报稿

日期：2026-04-03

## 用途

这份文档用于配合 3 页 PPT 做口头汇报。整体风格偏简洁，适合组会上用 3 到 5 分钟讲清楚核心思路。

---

## 第 1 页：为什么要从 AI workload 出发

### 页面标题

`为什么后续 GPU 研究应该从 AI workload 出发`

### 建议讲稿

这一页我想讲一个很核心的出发点，就是如果我们的目标是提升 GPU 在 AI 场景下的效率，那后续研究的起点不能只是一组传统微基准。

微基准当然有价值，因为它能帮助我们看 cache、memory、shared memory、atomic 这些局部机制。但是它的问题在于，它只能说明局部变了，没有办法直接说明真实 AI 模型端到端是不是更快了。

反过来，如果我们只看大模型，也会有问题。因为大模型的结果虽然真实，但通常很难直接解释清楚，到底是哪个 kernel、哪个硬件资源、哪一种机制在主导瓶颈。

所以我觉得更合理的方向，不是在“微基准”和“AI workload”之间二选一，而是让 AI workload 来定义真正重要的问题，再用微基准去解释这些问题背后的机理。

### 本页收尾句

所以这一页的结论就是：如果目标是 AI 场景下的 GPU 效率提升，那么 AI workload 应该成为问题定义的起点。

## 第 2 页：建议采用的研究闭环

### 页面标题

`建议采用的工作流：模型提出问题，模型验证结果`

### 建议讲稿

在这个出发点下面，我觉得后续工作最好组织成一条固定的闭环。

第一步，先定义目标 AI 场景，比如是 LLM 推理、长上下文、训练吞吐，还是某一类 attention-heavy workload。

第二步，做模型级模拟，先看端到端指标，比如吞吐、时延、memory traffic，先弄清楚问题到底出现在哪里。

第三步，在模型结果基础上去定位热点 kernel，也就是把“模型整体慢”进一步缩小成“哪几类操作慢”。

第四步，再用相关微基准去验证机理。比如如果怀疑是 memory hierarchy 的问题，就去看 cache 和 bandwidth；如果怀疑是 shared memory 或 atomic 的问题，就用对应微基准去拆。

第五步，在机理比较清楚以后，再提出有针对性的架构优化。最后还必须回到模型级 workload 上重新验收，看端到端收益是不是真的成立。

我觉得这一点特别重要，因为它能避免一种常见情况，就是先做了一个局部优化，然后再去找一个能证明它有效的场景。更合理的方式应该是，先让模型提出问题，最后再让模型验证结果。

### 本页收尾句

所以这一页的结论就是：最合理的研究方式，是建立一条“模型提出问题、微基准解释问题、模型验证结果”的闭环。

## 第 3 页：近期怎么落地第一轮工作

### 页面标题

`近期推进建议：先打通第一条小而完整的闭环`

### 建议讲稿

如果按这个方向往下推进，我觉得第一轮工作不应该追求覆盖面特别大，而是应该先把第一条闭环跑通。

具体来说，第一步可以先选一个代表性的 AI workload，不要一开始同时铺很多模型。

第二步，先只盯一类最主要的瓶颈。比如第一轮可以明确聚焦在 memory-bound 问题，或者聚焦在 attention / KV cache 相关问题，而不是把所有维度都摊开。

第三步，先跑出第一版模型级 baseline，先把端到端瓶颈看清楚。

第四步，再建立热点 kernel 和相关微基准之间的映射关系。也就是说，不是泛泛地跑一堆微基准，而是只跑那些能解释当前模型瓶颈的微基准。

第五步，只做一到两个明确的优化点，然后回到模型级 workload 再做验收。

我觉得第一轮最重要的目标，不是做很多实验，也不是追求一下子覆盖很多工作负载，而是先证明这条方法本身是能跑通的，是能形成闭环的。

### 本页收尾句

所以这一页的结论就是：近期最重要的不是把问题铺得很大，而是先建立一条“模型到瓶颈到优化再回到模型”的可重复闭环。

---

## 最后总结时可以直接说的话

如果最后需要用一句话做总结，可以直接这样说：

我们后续希望做的，不只是局部机制优化，而是建立一条由 AI workload 定义需求、由模型级模拟发现瓶颈、由微基准解释机理、并最终回到模型级 workload 验证收益的 GPU 研究闭环。
