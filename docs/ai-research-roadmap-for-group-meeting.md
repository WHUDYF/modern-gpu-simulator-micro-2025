# 面向组会讨论的 AI GPU 研究路线图

日期：2026-04-03

## 文档目的

这份文档用于组会讨论，目标不是展开某个具体实现细节，而是帮助统一一个大方向：

如果后续工作要围绕 AI workload 展开，应该如何组织研究路线、实验节奏和阶段性目标。

## 为什么需要从 AI workload 出发

如果研究目标是提升 GPU 在 AI 场景下的效率，那么出发点就不能只是一组传统微基准。

原因很简单：

- 微基准能说明局部机制是否强
- AI workload 才能说明这些机制是否真的有系统级价值

如果没有模型级 workload，很容易出现下面这些问题：

- 优化了一个局部指标，但模型整体不快
- 一个机制在 synthetic benchmark 上很好看，但在真实模型里并不重要
- 研究过程中不断增加细节，却缺少真正的应用牵引

因此，后续路线应当明确地以 AI workload 作为牵引对象。

## 大方向上的研究主线

建议把整体研究路线组织成下面这条主线：

`AI 场景需求 -> 模型级模拟 -> 热点分析 -> 微基准验证 -> 架构优化 -> 模型级回验`

这条主线的意义在于：

- 前半段决定问题是否真实
- 中间部分决定问题是否可解释
- 后半段决定优化是否真正有效

## 可以向组会说明的核心观点

### 观点 1：AI workload 是需求来源

研究不应该从“某个局部机制看起来可以优化”出发，而应该从“某类 AI workload 的真实需求”出发。

例如：

- 长上下文推理需要更好的 memory efficiency
- attention-heavy workload 需要更好的带宽与 cache 行为
- 推理场景可能更在意 latency
- 训练场景可能更在意 throughput 与能效

也就是说，AI workload 不是最后拿来展示结果的装饰，而应该是一开始就决定方向的输入。

### 观点 2：模型级模拟负责发现真正重要的问题

有了 AI workload 后，第一步应该先做模型级模拟，而不是先跳去调某个局部参数。

模型级模拟的价值在于回答：

- 哪类模型最受限
- 哪些阶段最耗时
- 哪些 kernel 真的值得关心
- 哪些瓶颈在实际应用中反复出现

只有先看到模型级行为，后面的优化才有实际意义。

### 观点 3：微基准负责解释“为什么”

当模型级模拟发现热点以后，再用微基准去拆解根因。

微基准在这个路线里的角色不是主角，而是分析工具。

它们主要用于：

- 验证 cache / memory / atomic / shared memory 等局部机理
- 帮助缩小设计空间
- 解释为什么模型会在某些阶段受限

这样微基准就不是孤立存在，而是服务于模型级问题。

### 观点 4：最终必须回到模型级做验收

任何局部优化最后都必须重新放回模型级 workload 中验证。

这一步需要检查：

- 端到端吞吐是否提高
- 时延是否降低
- 收益是否稳定
- 是否引入了新的副作用

如果没有这一层，研究很容易停留在“看起来有效”，而不是“在真实 AI 场景中有效”。

## 研究路线的三个阶段

### 第一阶段：建立第一条可闭环路径

目标不是覆盖所有 AI workload，而是先打通第一条完整链路。

建议：

- 选一个代表性模型场景
- 选一个最明显的瓶颈方向
- 做一轮从模型到微基准再回到模型的完整闭环

这一阶段最重要的是证明方法成立。

### 第二阶段：扩展到一类 workload

在第一条链路跑通后，再扩展到一类相近 workload。

例如：

- 不同 LLM 推理配置
- 不同上下文长度
- 不同 batch size
- 不同 memory pressure 场景

这一阶段的目标是验证优化是否具有泛化性。

### 第三阶段：形成系统性设计空间

当前两阶段结果比较稳定后，再把局部想法系统化。

这时可以进一步组织：

- 哪几类瓶颈最常见
- 哪些机制适用于哪些 workload
- 哪些设计存在 trade-off
- 是否能形成更完整的架构方向

这一阶段才适合上升到更系统的研究主张。

## 近期可以推进的具体事项

如果面向组会给出下一步计划，可以按下面方式组织：

1. 确定一个代表性 AI workload
2. 明确该 workload 的核心指标
3. 跑出第一版模型级 baseline
4. 识别主导时间的 kernel
5. 建立和这些 kernel 对应的微基准映射
6. 形成第一版瓶颈归因
7. 提出一两个小而清晰的优化点

这样组会讨论就能从抽象方向落到可执行任务。

## 讨论时值得提前说清楚的风险

组会里通常需要提前把风险讲清楚，不然路线容易显得过于理想化。

这里至少有几类风险：

- AI workload 太复杂，热点分析容易分散
- 模型级模拟成本高，实验节奏会比微基准慢
- 某些局部优化可能只对个别模型有效
- 模拟器配置与真实硬件之间可能存在偏差
- 如果没有严格回到模型级验证，容易高估局部优化价值

这些风险并不意味着路线不可行，只是意味着需要分阶段推进。

## 组会里可以强调的价值

这条路线的价值主要有三点：

- 它让研究问题更贴近真实 AI 需求
- 它让局部机制优化有明确应用牵引
- 它能形成一条可重复、可扩展的研究闭环

相比单纯堆微基准结果，这种路线更容易支撑长期工作，也更容易沉淀成系统性的研究框架。

## 推荐的组会表达方式

如果在组会上用一两页讲清楚，可以按下面顺序展开：

1. 先说明为什么“只看微基准”不够
2. 再说明为什么“只看大模型”也不够
3. 给出中间闭环：模型发现问题，微基准解释问题，模型验证结果
4. 说明当前阶段先做第一条闭环，而不是一次铺开所有模型
5. 最后给出近期任务和中期里程碑

这样逻辑会比较顺。

## 一句话版本

如果要用一句话概括这条路线，可以说：

`后续研究应当由 AI workload 提出真实需求，用模型级模拟发现瓶颈，用微基准解释机理，用架构优化解决问题，并最终回到模型级 workload 验证收益。`
