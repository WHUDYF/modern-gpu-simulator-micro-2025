# AI Workload 驱动的 GPU 研究工作流

日期：2026-04-03

## 目的

这份文档用于总结一个适合后续工作的总流程。核心目标不是只回答“某个局部机制是否更快”，而是建立一条从 AI 模型需求出发、经过模拟和瓶颈定位、再回到最终实现效果验证的完整闭环。

这个工作流面向的是长期研究方法，而不是某一次单独实验的操作手册。

## 为什么不能只看微基准

微基准很有用，但它只能回答局部问题，例如：

- L1、L2、HBM 的延迟和带宽够不够
- shared memory 是否存在冲突
- atomic 是否成为瓶颈
- 某类访存或调度模式是否存在明显低效

这些信息对于定位机理非常重要，但它们不能直接证明一个优化对真实 AI workload 是否有价值。

如果目标是提升 AI 场景下的 GPU 效率，最终必须回答的是下面这些问题：

- 端到端模型是否真的更快
- 吞吐、时延、能效是否真的改善
- 某个优化是否只提升了局部 kernel，却没有改善整体模型
- 某个优化是否在一个模型有效，但在另一类 workload 上失效

因此，只看微基准会得到“局部正确”，但不一定得到“系统层面有意义”的结果。

## 为什么也不能只看 AI 模型

只看 AI 模型也不够。

模型级 workload 是混合负载，里面同时包含：

- GEMM
- attention
- layernorm
- KV cache 相关访存
- reduction / synchronization
- kernel launch 和调度开销

如果只看到“模型整体慢了”或者“模型整体快了”，通常很难回答下面这些问题：

- 具体是哪个 kernel 在主导时间
- 是 compute-bound 还是 memory-bound
- 是 cache、带宽、同步、调度还是并行度的问题
- 应该优化哪一层机制，才能稳定产生收益

因此，只看模型会得到“端到端结果”，但很难得到“为什么如此”的解释。

## 核心思想

最佳方式不是在“微基准”和“AI 模型”之间二选一，而是建立分层闭环：

`AI workload 定义需求 -> 模型级模拟 -> 热点与瓶颈归因 -> 微基准验证机理 -> 架构/实现优化 -> 回到模型级验收`

这条主线里：

- AI workload 负责定义问题是否真实、优化是否值得做
- 微基准负责解释瓶颈机理、帮助缩小优化空间
- 模型级回验负责判断最终结果是否真的成立

## 分层工作流

### 1. 目标层：定义研究问题

第一步不是直接跑模拟器，而是先把研究目标说清楚。

需要回答的问题：

- 想优化的是训练还是推理
- 目标模型是哪一类
- 关注的是吞吐、时延、能效，还是成本
- 目标场景是短上下文还是长上下文
- 是 dense model、MoE，还是多模态模型

这一层的产出应该是一个明确的问题定义，例如：

- 提升长上下文 LLM 推理中的 memory efficiency
- 提升 attention-heavy workload 的吞吐
- 降低 KV cache 主导场景下的带宽压力

如果这一层不清楚，后面的模拟和优化很容易失焦。

### 2. 模型层：选择 AI workload 做端到端观察

在目标层确定后，选择代表性模型或 workload。

这一层关心的不是局部机制，而是端到端行为，例如：

- 总吞吐
- 单请求时延
- batch 变化下的表现
- 序列长度变化下的表现
- 模型不同阶段的时间分布

这一层需要回答：

- 哪些模型最能代表目标场景
- 哪些输入规模最能暴露瓶颈
- 哪些配置最值得作为 baseline

建议不要一开始就铺很多模型，而是先选少量但具有代表性的 workload。

### 3. Kernel 层：识别主要热点

模型级结果出来后，下一步不是立刻改架构，而是先找到主导时间的 kernel。

这一层要回答：

- 哪些 kernel 占了最多时间
- 哪些 kernel 占了最多 memory traffic
- 哪些 kernel 最影响吞吐或时延
- 哪些 kernel 在不同输入规模下会成为新的瓶颈

这一层通常会把问题从“模型整体慢”转成“某几类操作慢”。

常见热点包括：

- GEMM
- attention score / softmax / value update
- KV cache read/write
- layernorm / reduction
- embedding / gather / scatter

### 4. 机理层：用微基准验证瓶颈原因

当已经知道瓶颈大致落在哪一类 kernel 后，就可以用微基准去验证机理。

这一层不是重新寻找应用，而是围绕模型级热点做针对性的拆解。

例如：

- 如果怀疑 attention 的问题来自 cache miss，就看 L1/L2 行为
- 如果怀疑 KV cache 压力来自带宽瓶颈，就看 memory-bound 微基准
- 如果怀疑某类 reduction 被 atomic 限制，就看 atomic 系列微基准
- 如果怀疑 shared memory 使用不合理，就看 shared_bw / shared_lat 相关结果

这一层要回答的是：

- 慢的根源是什么
- 哪个硬件资源先饱和
- 哪个微观机制最值得优化

### 5. 架构层：提出优化方案

在确认瓶颈机理后，再提出架构或实现层改动。

可能的方向包括：

- cache 容量或 cache policy 调整
- prefetch 或 data placement 机制
- memory scheduling 策略
- shared memory 组织方式
- warp scheduling 或 issue 策略
- 针对 AI workload 的专门支持，例如 KV cache 友好机制
- interconnect 或集体通信优化

这一层的关键不是“做了一个改动”，而是“这个改动明确对应前面识别出来的瓶颈”。

### 6. 回验层：重新回到模型级 workload

局部优化完成后，必须回到最初的 AI workload 上重新验收。

这一步要回答：

- 模型端到端是否真的提升
- 改进是否稳定存在
- 是否只提升了某个 kernel，但模型整体收益很弱
- 是否在某些输入规模下出现回退

这是整个工作流中最重要的闭环步骤。如果没有这一层，研究很容易停留在“局部机制看起来更强”，但没有证明它对真实 AI 场景有效。

## 一条完整的闭环

可以把整个流程压缩成下面这条链路：

1. 先定义 AI workload 需求
2. 选取代表性模型与输入规模
3. 做模型级模拟，观察端到端指标
4. 找出主要热点 kernel
5. 用微基准验证瓶颈机理
6. 设计有针对性的架构优化
7. 回到模型级 workload 做验收
8. 比较优化前后在不同场景下的收益与代价

这个流程强调的是“问题驱动”，而不是“先做一个局部优化，再去找能证明它有效的 workload”。

## 推荐输出物

为了让后续工作更可执行，建议每一轮研究都沉淀下面这些输出物：

- 一页问题定义
- 一组模型级 baseline 结果
- 一张热点 kernel 排序表
- 一份瓶颈归因说明
- 一组对应的微基准结果
- 一份架构改动说明
- 一组优化后模型级回验结果

这样做的好处是每一层都有清晰交付物，不容易在中途丢掉上下文。

## 如何启动第一轮工作

如果要把这个方法真正落地，建议第一轮不要追求“大而全”，而是按下面方式收敛：

1. 只选一个 AI 模型场景
2. 只关注一类最主要的瓶颈
3. 只挑少数几个最相关的微基准
4. 只提出一两个有明确指向的优化点
5. 一定要回到模型级做最终验证

这样更容易形成第一条真正闭环的样例。

## 一个简短示例

下面给出一个示例，仅用于说明流程，不代表已经确定的最终课题：

1. 目标：提升长上下文 LLM 推理效率
2. 模型层观察：发现推理阶段 memory traffic 很高，吞吐下降明显
3. Kernel 层归因：KV cache 读取相关 kernel 占据主要时间
4. 机理层验证：memory / cache 相关微基准显示带宽和 cache 行为是主要约束
5. 架构层优化：提出更适合 KV cache 访问模式的 cache / data placement 机制
6. 回验层检查：回到 LLM 推理 workload，看 tokens/s 和 latency 是否真正改善

这个示例体现的不是某个具体方案，而是“从模型问题出发，最后回到模型验证”的方法。

## 后续展开建议

后续工作可以沿三个方向展开：

- 从模型维度扩展：覆盖不同类型 AI workload
- 从瓶颈维度扩展：区分 compute-bound、memory-bound、communication-bound 场景
- 从优化维度扩展：把局部机制优化组织成更系统的架构设计空间

如果后续工作始终围绕这条闭环推进，就能避免研究偏离真实 AI 场景，也能避免只停留在局部机制分析。

## 一句话总结

这套工作流的核心不是“先做微基准”，也不是“只跑大模型”，而是：

`用 AI workload 定义问题，用模型级模拟发现瓶颈，用微基准解释机理，用架构优化解决问题，再回到 AI workload 验证结果。`
