# B 线方法论修正备忘

日期：2026-04-24

## 1. 文档目的

这份文档用于收束当前对 B 线的最新方法论判断，作为下一轮修改 B 线工作时的统一依据。

当前需要修正的，不是 B 线是否存在，而是：

- B 线到底在承接 A 线的什么结果
- `anchor / family / regime / lane` 四层对象之间的职责边界是什么
- 我们所说的“算法分组”和“硬件分组”分别指什么
- family 为什么不能简单等同于 anchor
- 后续修改 B 线时，应该朝什么方向收敛

---

## 2. 当前共识

当前可以先把整条链条理解成：

`compression / anchor -> B 线结构分析 -> backend decision objects`

更具体地说：

1. A 线负责把原始 workload 压成 representative anchors。
2. 这种压缩会保留代表性，但一定会折叠掉一部分上下文、功能角色和硬件敏感性信息。
3. B 线的职责不是重复 A 线，而是对这些 anchors 做更精确的结构分析。
4. 这种结构分析至少包含两部分：
   - 算法功能分析
   - 硬件执行分析
5. 最终目标不是“多做一张总结表”，而是得到 backend 真正能消费的决策对象。

因此，B 线的正确定位不是：

- 信息汇总层
- 文档解释层
- 对 A 线结果的重命名层

而是：

**把压缩后的代表对象重新提升成可干预、可验证、可回写的 backend decision objects。**

---

## 3. 对 A 线结果的最新理解

当前对 A 线最稳妥的理解应当是：

**前端压缩尽量把行为相似、工作形式接近、可以由同一个代表对象近似的 kernels 聚到一起。**

这里不要把 A 线说成：

- “把功能相同的 kernel 分在一起”
- “已经恢复了完整算法语义”

因为这会把 A 线说得过满。

更准确的说法是：

1. A 线完成的是 representative compression。
2. anchor 代表的是一组“可由一个代表对象近似”的 kernel。
3. 这个代表过程天然会丢失一部分：
   - 细粒度上下文
   - 功能角色信息
   - backend 关心的硬件敏感性差异

所以 A 线不是最终答案，而只是 B 线的输入对象层。

---

## 4. 算法分组与硬件分组

这是本轮修正里最重要的一点。

### 4.1 什么不是算法分组

算法分组不应再理解成：

- QKV projection 一组
- softmax 一组
- FFN expand 一组

这种说法仍然过于贴近具体模型模块和算子名字，容易退化成“按算子名/模型块贴标签”。

这不是我们要的普适信息。

### 4.2 算法分组的正确定义

算法分组应当理解为：

**按 kernel 在整体计算流程中的计算功能角色来分。**

它回答的是：

- 这个 kernel 是不是主体计算核
- 是不是中间变换核
- 是不是归约/归一化核
- 是不是聚合/融合核
- 是不是逐元素后处理核
- 是不是搬运/重排/约束性 kernel

因此，算法分组更像是一层：

**function-of-computation grouping**

也就是“它在做什么计算功能”。

一个更普适的算法分组空间可以写成：

- `primary_compute`
- `score_or_transform`
- `reduction_normalization`
- `aggregation_or_fusion`
- `elementwise_postprocess`
- `layout_or_data_movement`
- `constraint_or_bookkeeping`

这层信息的价值在于：

- 它不绑定具体模型名
- 它不绑定具体算子名
- 它保留了 kernel 在算法流程中的职责信息

### 4.3 硬件分组的正确定义

硬件分组应当理解为：

**按 kernel 在 GPU 上的执行模板、资源行为和预期调参方向来分。**

它回答的是：

- 它属于哪种执行模板
- 它对哪类资源更敏感
- 它更像哪类硬件等价对象
- 后端应优先朝哪个参数方向验证

因此，硬件分组更像：

**execution-template grouping**

也就是“它在 GPU 上怎么跑”。

在你们当前 B 线对象里，family 更接近这种分组。

### 4.4 两者的关系

算法分组和硬件分组不是互斥关系，而是两套不同的信息轴：

- 算法分组看“做什么”
- 硬件分组看“怎么跑”

这两套信息都要保留，但它们不应承担同样的对象职责。

---

## 4.5 A 线还必须带出权重信息

如果 B 线后续要讨论：

- 哪些对象更重要
- 哪些对象更值得优先进入 regime / lane
- 某个 family 的主导压力到底来自谁

那么 A 线输出就不能只有“代表关系”，还必须带出代表对象的权重信息。

也就是说，A 线不应只告诉我们：

- 哪个 anchor 代表了哪一组 kernel

还应尽量告诉我们：

- 这个 anchor 覆盖了多少成员
- 这组对象覆盖了多少时间
- 这组对象的大致工作量有多大

因此，A 线至少应为 B 线保留三类基础统计：

1. `membership`
   代表对象覆盖了多少原始 kernel / invocation。

2. `time weight`
   这一组对象在总执行时间里大约占多少。

3. `workload scale`
   例如平均动态指令数、总动态指令数、平均执行时间或其他能代表工作量的统计量。

这一步的意义在于：

- B 线不仅要知道“谁是独特对象”
- 还要知道“谁是重要对象”

否则就会出现一种风险：

- 某个 anchor 在结构上非常独特
- 但它只覆盖极少数成员、极少时间
- 却在后续 B 线里被过度放大

因此，A 线对 B 线最有价值的输出，不只是：

- `who represents whom`

还应包括：

- `how much this representative object matters`

这也是为什么后续如果参考 STEM 类方法，最值得吸收的不是整套方法外观，而是：

**代表对象必须同时带出 membership、time weight 和 workload scale 这类权重信息。**

---

## 5. anchor 和 family 的关系

这是当前 B 线最需要想清楚的地方。

### 5.1 为什么 family 可能会和 anchor 很像

这在第一版里是合理的。

如果 A 线已经把一批 kernel 压成了相对纯净的 representative anchors，那么到了 B 线之后，确实可能出现：

- 一个 family 只含一个 anchor
- family 与 anchor 边界高度相似
- B 线没有发生大规模重新合并

这是因为：

1. 当前 workload 很小，只是一层 transformer。
2. 当前 anchor 本身已经压得比较细。
3. 小规模场景下，A 线和 B 线天然会显得更接近。

所以：

**第一版里 family 和 anchor 高度相似，是合理现象。**

### 5.2 但 family 不能被定义成 anchor 的重命名

虽然第一版里它们可以很像，但方法上不能把它们等同。

因为它们回答的问题不同：

- `anchor` 回答的是：
  - 哪些 kernel 可以由同一个代表对象近似
- `family` 回答的是：
  - 哪些 anchors 在硬件执行模板上属于同一大类

因此：

- anchor 更像“代表性对象”
- family 更像“硬件等价类”

这也是为什么即使 family 暂时与 anchor 很像，family 这层仍然要保留。

### 5.3 什么时候 family 才真正提供了额外价值

当 family 至少满足下面任一情况时，它就不再只是重复 anchor：

1. 它把多个算法功能不同、但硬件模板相同的 anchors 合并到了一个硬件大类里。
2. 它把后端调参方向统一到了一个共享 hardware route 上。
3. 它能为后续 regime 拆分提供更稳的“硬件上层边界”。

如果 family 完全不能多提供这些内容，那么 B 线就会变薄。

---

## 6. B 线四层对象的重新定义

基于上面的修正，当前更合理的四层定义如下。

### 6.1 anchor

anchor 是 A 线输出的 representative object。

它代表：

- 一组行为相近、工作形式接近、可由同一个代表对象近似的 kernel

它的职责是：

- 先把原始 workload 压成可处理对象

它不负责：

- 完整算法解释
- 完整硬件解释
- 直接决定 backend 参数方向

### 6.2 family

family 是 B 线构造的硬件大类对象。

它代表：

- 一组在执行模板、资源行为和后端调参方向上具有同类性的 anchors

它的职责是：

- 提供硬件上层边界
- 提供 backend-side hardware equivalence
- 为后续 regime 拆分提供共享的大框架

因此，family 应主要由：

- 硬件分组

来决定。

### 6.3 regime

regime 是 family 内真正进入 backend 单独验证的对象。

它的职责是：

- 在共享硬件大类内部，把仍然不能混在一起的对象拆开

regime 的拆分依据不应只看硬件，也不应只看算法，而应同时参考：

- 硬件大类一致性
- 算法功能角色
- shape / context
- resource signature
- 是否会改变 parameter direction

因此：

**regime 是算法功能分析和硬件分析真正汇合的位置。**

### 6.4 lane

lane 是 regime 到 backend 调参/验证入口的映射。

它的职责是：

- 把 regime 变成实际可干预、可验证的参数方向

lane 主要落回：

- 硬件敏感方向
- backend 验证入口
- writeback 协议

---

## 7. 当前对 B 线职责的最终表述

基于这轮讨论，B 线的职责最适合表述为：

**在前端压缩得到 representative anchors 之后，结合算法功能分析和硬件执行分析，把这些代表对象重新组织成 backend 可以实际使用的结构化决策对象。**

如果再压缩一点，可以写成：

**A 线负责“先代表起来”，B 线负责“再解释清楚并组织成可调对象”。**

---

## 8. 对后续修改 B 线的直接要求

下一轮修改 B 线时，应按以下方向收敛。

### 8.1 不要把算法分组写成算子分组

后续任何文档、表格、代码注释里，如果要写“算法分组”，都不应再直接等同于：

- attention
- FFN
- layernorm
- residual

更稳妥的写法应当是：

- 主计算
- 中间变换
- 归约/归一化
- 聚合/融合
- 逐元素后处理
- 数据搬运/约束类

### 8.2 family 应更明确地承担硬件分组职责

family 的判断标准应优先落在：

- 执行模板
- route primitive
- 资源敏感性
- 共享调参方向

而不是：

- 算法名相近
- 模型位置接近

### 8.3 regime 应成为“两套信息的交汇层”

regime 的拆分，不应被理解成“family 的细一点版本”，而应明确为：

- 在同一硬件 family 内
- 进一步引入算法功能角色和上下文
- 决定 backend 是否必须单独看

### 8.4 接受第一版里 family 与 anchor 高度相似

当前不要为了“让 family 看起来更有存在感”而强行制造复杂度。

第一版里允许：

- family 和 anchor 高度相似
- 单 anchor family 存在

但需要在方法上明确说明：

- 这不是定义上的等同
- 而是小 workload、细 anchor 条件下的自然结果

### 8.5 后续要验证 family 是否真的有独立价值

未来扩大 workload 后，需要重点观察：

1. family 是否开始跨多个 anchors 提供稳定的硬件大类
2. family 是否真的能统一 backend 调参方向
3. 去掉 family 之后，regime / lane 是否变得更混乱

只有这些证据出现，family 的方法价值才会进一步坐实。

---

## 9. 建议的修改顺序

如果下一轮要按 RLCR 或其他方式修改 B 线，建议顺序如下：

1. 先统一文档口径  
   明确算法分组、硬件分组、anchor、family、regime、lane 的定义。

2. 再检查 YAML / builder 中 family 的判据  
   看是否有明显把算法名当成 family 判据的地方。

3. 再检查 regime 的拆分逻辑  
   看是否真正体现了“算法功能角色 + 硬件大类”的联合判断。

4. 最后再看 lane  
   确认 lane 仍然服务于 backend 参数方向，而不是重新承载语义分类。

---

## 10. 结论

这轮讨论后，B 线最重要的修正可以压成三句话：

1. 前端压缩负责先把 kernel 代表起来，但一定会折叠掉一部分信息。
2. B 线的任务不是重复压缩结果，而是对这些 anchors 做算法功能分析和硬件执行分析。
3. family 主要承接硬件分组，regime 才是算法功能信息和硬件信息真正汇合并进入 backend 的对象层。

因此，后续修改 B 线时，应避免两种退化：

- 退化成“对 A 线结果的重命名”
- 退化成“按算子名做语义贴标签”

而应持续朝下面这个目标收敛：

**把 representative anchors 重新提升成有硬件边界、有功能解释、能指导 backend 调参与验证的结构化对象系统。**
